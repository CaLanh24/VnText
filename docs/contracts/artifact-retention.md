**Owner cleanup decision (2026-10-27):** Owner: “sửa quy tắc cleanup cho rõ rồi bảo brain dọn những thứ k còn cần đi, đừng để ảnh hưởng task đang chạy, cũng đừng cứ giữ rác mãi vì lý do evidence nữa.” This is a specific cleanup authority for the current workflow, not authority to delete user data or relax a guard. (1) Every allocation/artifact has owner, task, absolute path, data kind, size, current consumer, expiry condition and cleanup step; RETAINED, UNKNOWN or “evidence” alone never creates open-ended retention - retention needs a concrete consumer and a review point (phase/checkpoint or date). (2) Classes: source/user data/Git and the shared environment in use; candidates, baselines and fixtures with an open acceptance or release-route consumer; disposable or repro copies with no consumer. Totals, shared environment, active and disposable bytes are reported separately and compared with the cap that applies to each (the terminal cap does not include the shared environment). (3) After each phase and before a large allocation, scratch, output and build copies without a consumer are removed; at task end every disposable is removed except listed exceptions with an expiry. An open release does not keep an older task's or release's artifacts alive, and stale unused copies are not kept until publication. A defective copy is kept for repro only while its finding is open; closing the finding means collecting a compact receipt and removing the repro. Being re-downloadable does not authorise removing a model or SDK needed offline; shared caches are checked per consumer, never bulk-deleted. (4) Evidence defaults to a compact receipt: source/candidate SHA, command and exit code, verdict and limits, hash/count/bytes, finding and the necessary screenshot/log excerpt, with the payload recorded as disposed (never implying a deleted artifact can be re-run). No installer, full extracted tree, bulk test builds or duplicate caches kept only as proof. Target <= 20 MiB per task at terminal; a larger amount needs a specific reason and review date, and essential acceptance information is never cut to hit the number. Immutable epoch-chain snapshots stay only with a precise integrity consumer and review date; compacting them needs a separately reviewed route and is not part of routine cleanup. (5) UNKNOWN items are investigated at the next cleanup checkpoint (owner, Git, process, consumer); missing registration alone is not authority to delete. If ownership cannot be established, record the concrete question, the responsible owner and the next review point and continue with independent targets. (6) A cleanup run uses a plan with absolute paths, expected bytes, ownership/no-consumer evidence and exclusions; checks processes, file locks, writers, transactions, CU sessions, links/junctions and worktrees before mutating; revalidates that each target is inside the root named by the Owner without following links out; never kills shared processes, resets, stashes or deletes dirty source; uses the helper/registry lifecycle and updates tombstone/receipt; never edits a validator or deletes the active epoch to gain quota. It runs on the same sole DEV at a safe boundary (not parallel to a source writer, test or native run using the artifact). If a guard blocks a truly safe cleanup, the run reports the guard and a bounded solution and continues with other authorised targets; it does not open a cleanup refactor campaign. (7) Reports give before/after bytes, removed paths, what is kept with consumer and expiry, processes, and a cleanup verdict separate from gate verdicts; deletion is claimed only after readback. Cleaning disposable artifacts or fixing rules does not require rebuilding or a full test run.

**Patch cancellation boundary (release 0.1.13, 2026-10-27, corrected after review):** a host cancel during Patch is honoured while the per-target read-back verification runs (the verifier child is terminated and reaped, polled about every 0.5 s) and at every writer progress point. If the output directory was never created the statement says the cancel came before anything was written. Patch only writes into its output directory; the source game is not modified by this step. The WPF shows that statement for a cancelled Patch instead of the translate wording. A cancel first observed at the final progress event (after the verification report and import report exist) cannot stop anything: the run finishes `ok` with a summary that starts with “Yêu cầu hủy đến quá muộn”, never a cancelled terminal over a completed patch. Tests: `tests/unit/test_patch_cancel_boundary.py` (byte-identical output after a cancel with nested foreign data, a user file under an artifact name, a pre-existing empty directory, a symlink/junction and a never-created output; read-only statement helper; too-late result; verifier child terminated promptly) and the WPF harness case `PatchCancel_StatesTheOutputAndNeverUsesTheTranslateCopy`. **Invariant:**

- Every artifact under `TEST_RUN` is classified as `PROTECTED`, `RETAINED`, `DISPOSABLE`, `UNKNOWN`, `MISSING` or `STALE`, and registered with a non-empty owner and purpose. `artifacts_manifest.json` is the only registry; `cleanup_manifest.json` is a run report.
- **Feature lifecycle:** one task may use one `.dev-env`, one current `DEV_RUN` build and one disposable `TEST_RUN`. Focused tests stream a bounded summary (maximum 10 MiB) before terminal cleanup; the final bounded Markdown receipt lives under `DEV_RUN/runner-reports`, outside the transient root. After `PASS`, `FAIL`, `TIMEOUT`, `START_ERROR` or `CANCELLED`, `TEST_RUN` must be absent/empty unless the task explicitly sets `OWNER_TEST_PENDING=1`. If a verified prospective epoch already owns retained control-plane/release evidence, a wrapper may preserve only the verified epoch files/registry, unchanged registered release-gate evidence, append-only cleanup history, empty registered `tmp` containers, and previously registered canonical runner receipts whose path, owner, purpose, size and content hash verify; all payload, changed/unrecognized paths, incomplete inventory, or non-RETAINED lifecycle still forces `REVIEW_REQUIRED`. This exception does not make a failed test pass. Game copies, transient logs and caches remain disposable. A new task cannot start while a prior transient root is non-terminal or unknown.
- **Computer Use lifecycle:** initialize a Windows UI-control session only immediately before a required native interaction. When that interaction ends, work switches to backend validation/waiting, or a turn is interrupted, reaches usage limits or errors, cancel pending input/capture and dispose/reset the task-owned session/kernel with its supported API. Closing the target app alone does not end Computer Use. Never leave input/capture loops running while idle or terminal. On resume, check for orphaned task-owned sessions/actions before creating another. Distinguish task-owned sessions from shared Codex/tool-server processes; do not kill shared Node/Codex processes without proven ownership. Terminal receipts record reset/dispose status, pending actions and owned app/worker processes; use `UNKNOWN` when ownership or terminal state cannot be verified.
- **Release lifecycle:** `RELEASE_RUN` is created only for an explicit Release task and may retain one baseline/candidate/evidence scope until acceptance. After publication and acceptance, retain only the compact canonical receipt; dispose payload copies and staging. Release evidence does not authorize a second environment or a persistent `TEST_RUN`.
- `TEST_RUN/game-copy` is protected from generic cleanup but is a temporary test copy, never a retained fixture/baseline. For every game-test outcome, first save needed reports/logs outside the copy and ensure the test process has exited. The canonical copy uses `dispose_e2e_game_copy`; a scoped copy must be registered at its exact root as `kind=test_game_copy`, `lifecycle=DISPOSABLE` and passed to `cleanup_after_test(..., disposable_paths=[copy])` with the actual test outcome. Both routes record terminal `MISSING`. Canonical non-game fixtures, user/game paths, models, baselines and retained evidence remain protected. Cleanup targets must stay under `TEST_RUN`; outside/protected paths are rejected and no process is killed to make deletion possible.
- An ACTIVE legacy entry whose path is absent becomes `MISSING`/`STALE`; an existing root without a registry entry becomes `UNKNOWN` unless an explicit protected/retained path rule covers it. Neither case is silently dropped or deleted.
- `--dry-run` performs no `TEST_RUN`, registry or evidence write; only an explicitly requested `--output` outside `TEST_RUN` may be written. Generic cleanup deletes only registered `DISPOSABLE` artifacts (plus the explicit audited migration allowlist). After `PASS`, `FAIL`, `TIMEOUT`, `START_ERROR` or `CANCELLED`, the runner streams the exact outcome/exit/command/test summary/error and bounded stdout/stderr excerpts, then disposes terminal `TEST_RUN` content. Raw logs and heavy disposable payload are not retained for debugging. If the child remains alive, do not finalize or claim cleanup success; report its PID and `REVIEW_REQUIRED`. Test verdict and cleanup status remain separate.

Dry-run reports the blocker, never a planned deletion; apply rechecks the same ownership guard immediately before removal. `PROTECTED`, `RETAINED`, `UNKNOWN`, `STALE`, external/user paths and descendants claimed by those entries remain untouched.
- Registry reads used for updates reject linked/nonregular files, unreadable or malformed JSON, non-object roots and invalid `artifacts`/`archive` container shapes. Reconciliation never rewrites malformed registry metadata; cleanup remains `REVIEW_REQUIRED` until it is resolved.
- Every canonical run carries `scope_id`, `run_id`, `scope_root` and provenance, captures before/after inventory, and finalizes lifecycle in `finally`. New or modified paths outside the current scope registration are UNKNOWN/review-required. Cleanup status and before/after/deleted/retained/protected/unknown/locked data are evidence; cleanup failure cannot be hidden behind a child test PASS.

Await the entire canonical wrapper's terminal state, complete cleanup, and persist its receipt before starting another run or dependent phase. Child process exit alone is insufficient; canonical wrappers must never overlap, including during reconciliation. If overlap creates UNKNOWN records, prove exact ownership from primary run receipts before canonical API reconciliation and cleanup; never delete UNKNOWN paths blindly. The canonical manifest remains the full record source, and historical reports are not rewritten.
